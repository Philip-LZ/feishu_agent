# 第七章：测试与可靠性——怎样证明 Agent 系统真的工作

本章回答：“模型输出不确定，怎么测试？Mock 到什么程度？安全测试通过能证明什么？怎样验证重试、并发和记忆？”沿用直接提供答案的形式。

## 1. 先把系统保证拆成可观察行为

“Agent 可靠”过于笼统，应该换成可失败的断言：

| 保证 | 有效验证 |
| --- | --- |
| 同会话串行 | 记录实际进入/退出 Agent 的顺序，断言同 key 不重叠。 |
| 跨会话并发 | 用事件屏障确认两个不同 key 都进入执行，避免只测墙钟耗时。 |
| 安全拒绝 | 走框架工具执行入口，断言副作用替身调用次数为 0。 |
| 跨 session 记忆 | 检查目标文件内容，切换 session，再验证读取与召回。 |
| 观测脱敏 | 捕获每个输出出口，断言合成 secret 从未出现。 |
| 超时停止 | 断言返回超时之后任务不再产生副作用，不能只检查抛 TimeoutError。 |

测试要能在保证被破坏时失败。测试名、覆盖率、非空回复都不能替代这一步。

## 2. 单元、集成与 E2E 按边界区分

单元测试验证小范围逻辑，例如 PermissionGate 的 allow/warn/deny、Registry 的异常传播。可以直接构造输入，替换网络和模型，运行快速且结果稳定。

集成测试验证真实组件的连接，例如 Adapter → Registry → PermissionGate，或真实 CrewAI → Hook → 无害工具。它不必调用真实模型；测试目标是连接边界，就只替换目标之外的部分。

E2E 选择一个系统入口验证到输出的路径。当前 TestAPI 可以走真实 Runner、SessionManager，再选择假 Agent 或真实 Crew。是否使用 LLM 与是否贯穿应用链路是两个维度。

当前 `tests/integration/` 的部分夹具会查询远端 Langfuse；`tests/e2e/` 有依赖真实模型和沙箱的夹具。不要凭目录名猜测测试是否离线。

## 3. 为什么假 Agent 很有价值

[`tests/e2e/conftest.py`](../tests/e2e/conftest.py) 中的 `_echo_agent_fn()` 返回固定字符串，被注入真实 Runner：

```text
HTTP TestAPI
→ InboundMessage
→ Runner + SessionManager
→ echo AgentFn
→ CaptureSender
→ HTTP 响应
```

这样可测试命令、路由和会话，而不把模型随机性、token 费用和网络抖动混进断言。

但假 Agent 不能证明技能选择正确、MCP 兼容或模型输出有效。替换哪个依赖，就要承认该依赖的真实行为没有被这一层覆盖。

## 4. Mock 调用成功与真正写入不同

[`test_memory_index_flow.py`](../tests/unit/test_memory_index_flow.py) 把 `async_index_turn` 替换成 AsyncMock，运行 Runner，等待 shutdown，再检查参数。

这个测试证明成功对话会调度索引函数，并传入正确的会话、路由与文本。它没有证明 embedding API 成功、数据库事务提交或检索能找到数据。

完整验证还需要分别检查索引函数与外部服务的协议、写入内容，以及检索结果。测试报告应准确说“索引调度测试通过”，不能说“向量记忆已全面验证”。

## 5. 安全测试最容易出现假安全感

当前 `test_guardrail_deny_flow.py` 中的用例能直接检查 Registry 抛 deny、Adapter 保存 pending deny、callback 重抛。它们没有执行一个真实框架工具来证明调用被跳过。

有效的阻断集成测试应该把一个无害计数工具放进实际框架执行链，配置 deny，再断言：

```text
拒绝原因正确
工具执行次数 = 0
清理发生
后续正常请求仍可运行
```

这无需执行危险命令，也无需依赖真实模型生成恶意参数。第五章的执行前阻断缺口，正是局部单测通过却仍可能存在的连接问题。

## 6. 测试替身本身也需要符合协议

[`CaptureSender`](../xiaopaw/api/capture_sender.py) 按 msg_id 保存 Future，但发送回复时选择第一个未完成 Future，没有按 routing_key 或请求标识匹配。

如果两个并发请求以相反顺序完成，就有回复串给错误请求的风险。routing E2E 的快速 Echo 恰好顺序完成，不能证明任意耗时下都不会串话。

验证这个边界时，应主动让先提交的请求后完成。测试替身可以简化外部渠道，但不能丢失对目标行为至关重要的关联语义。

## 7. 并发测试怎样避免依赖运气

不要只写 `sleep(0.1)` 后猜测 worker 已进入某个状态。使用 `asyncio.Event` 建立可控时序：

```text
Agent A 已进入 → 测试收到信号
测试投递 A2 和 B1
检查 B1 可进入、A2 尚未进入
释放 A → 检查 A2 才开始
```

空闲退出竞态也要控制到“超时已发生，清理尚未执行”的边界。断言最终消息被消费、队列有活消费者，不能只检查 generation 数字增加。

给等待设置短而合理的超时，失败应尽快暴露。一次通过不能证明所有并发时序，但可控地覆盖已知危险交错比反复随机跑更有解释力。

## 8. 真实模型测试要同时看行为与结果

Agent 表达可以变化，因此不宜比较整段自然语言是否完全相等。对文件生成任务，优先验证文件存在、格式可解析、必要内容与路径正确，再检查回复。

[`test_e2e_07_memory_save.py`](../tests/e2e/test_e2e_07_memory_save.py) 同时检查保存回复、宿主机 user.md、`/new` 和新会话召回，比仅检查“已记住”更接近实际能力验证。不过关键词通过仍不能证明所有事实准确，也不能证明多用户隔离。

真实模型测试可固定输入集、记录模型/提示/技能版本、重复测量任务成功率、成本与耗时。单次成功只是一个样本；失败应保留工具轨迹和输入，不能简单多跑几遍直到通过。

## 9. LLM-as-Judge 的边界

当前 `llm_assert()` 把回复和标准交给另一个模型判断，但缺少 key 或评判 HTTP 响应非 200 时，退化为“回复非空”。这会让语义测试在评判服务不可用时仍显示成功。

有效的评判流程应区分任务不合格、评判器故障、环境不满足；评判器故障不能转换成通过。结构、路径、权限和副作用应优先使用确定性断言，语义质量再用明确标准评判，并保留人工抽查。

另一个例子是 `test_agent_does_not_infinite_loop`：当前只要求有限测试时间内返回非空回复，未检查循环次数、工具次数或 LoopDetector 的拒绝证据。它验证了一次请求能够返回，无法证明一般性的防循环保证。

## 10. 重试、超时与 shutdown 需要观察结果

重试可能重复产生副作用。网络超时只能说明客户端没收到结果，服务端可能已创建文档或发送消息；有副作用的接口需要请求关联、幂等键或结果核对。

当前 `async_retry()` 的 `max_retries` 实际控制总尝试次数：默认 3 表示最多执行 3 次，不是首次加 3 次重试。RetryTracker 只观测，不负责触发重试。

线程超时不等于线程取消。测试应确认超过期限后任务是否仍在运行，副作用是否继续。

当前 Runner.shutdown 取消 worker、等待后台索引任务，没有统一的索引等待期限。可靠性测试应覆盖停机时的执行中任务、排队消息与慢索引，并明确采用丢弃、等待还是可恢复交接策略。

## 11. 隔离与运行测试的安全范围

普通单测应使用 tmp_path、合成凭证和无害工具。当前 `sandbox_client` 会调用 `_clean_sandbox_workspace()`，清理挂载目录中的非模板根文件并覆盖模板，测试结束还会再次清理。

因此真实沙箱测试必须使用专门的测试 workspace；看到 tmp_path 夹具不能推断所有写入都在临时目录。Langfuse、飞书与数据库测试也应与个人/生产数据分离。

## 12. 覆盖率、通过与跳过分别说明什么

- 覆盖率说明代码被执行的范围，不说明断言充分或风险已覆盖。
- passed 只说明当前输入、环境和断言成立。
- skipped 说明该项没有验证，不能计入通过。
- failed 需要区分产品缺陷、测试缺陷、依赖/环境问题，并记录证据。

当前 pyproject.toml 配置覆盖率采集范围，但默认 pytest 配置没有强制运行 `--cov` 或覆盖率门槛。不能把设计文档中的目标覆盖率当成当前实测值。

## 13. 面试问题与直接答案

**问：不调用真实 LLM，怎么测试 Agent 项目？**

答：用假 AgentFn 验证确定性应用逻辑；用框架与无害工具验证调用接线；最后用真实模型、沙箱和小规模任务集验证决策和执行能力。每层说明替换范围和证据边界。

**问：集成测试已经有 deny 异常，还需要什么？**

答：需要断言实际工具函数没被执行。异常可能在副作用之后才抛出，单独检查异常不足以证明阻断。

**问：怎样测试记忆？**

答：分别验证写入正确位置、加载路径正确、切换 session 后可召回、更新不覆盖其他事实，以及不同用户的访问隔离。

**问：模型判断回复正确，可以作为唯一验收吗？**

答：不可以。先验证结构与副作用等确定性结果，再评估语义；评判器故障必须单列，不能退化成通过。

**问：测试多是不是项目就可靠？**

答：要看关键失败模式是否有有效断言，尤其并发、授权前阻断、持久化和超时后副作用。大量普通成功路径不能替代这些边界。
